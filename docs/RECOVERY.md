# TimeMaster V2 0.1.3 产物恢复与源码重建记录

## 结论

Git 仓库最初只保存了 LiteCal 0.1.0 的一次源码提交。之后演进成 TimeMaster V2 0.1.3 的工作目录没有进入版本控制，当前磁盘中也未找到该原始开发工程。后续功能并不是被 Git 删除了，而是从未在受版本控制的工作树中提交。

项目所有者保留下来的权威产物是最终 Windows 安装包。仓库据此完成了两件不同的工作：

1. 在 `runtime/` 保存从原始 0.1.3 `app.asar` 提取的、按哈希锁定的不可变运行时参考，并以 `v0.1.3` 标记该历史发布边界；
2. 在 `src/` 建立可编辑、可构建的 **source-equivalent reconstruction**，作为 0.1.4 及后续开发输入。

第二项不是“找回原始源码”。安装包不含 source map，也不含原始 Vue 单文件组件，因此无法恢复丢失工程的精确模块边界、模板格式、未使用代码或构建环境。

- Authenticode：**未签名**

从安装包提取的 `app.asar` 与当时已安装版本逐字节哈希一致。`runtime/` 中 10 个文件逐一与该 ASAR 核对，差异数为 0；各文件哈希保存在 [`docs/runtime-0.1.3.sha256`](runtime-0.1.3.sha256)。

原始安装包应只从本仓库 [GitHub Releases](https://github.com/bigelephant-code/TimeMasterV2/releases) 获取，并核对 Release 附带的 SHA-256。由于没有 Authenticode 签名，Windows 无法验证发布者身份，SmartScreen 可能给出警告。哈希一致只能证明文件与发布副本相同，不能替代代码签名或安全审计。

## 只读恢复方法

1. 将 NSIS/Electron 安装包作为 7z 容器只读提取。
2. 提取 `resources/app.asar` 并计算 SHA-256。
3. 使用 ASAR 工具展开主进程、preload、HTML、CSS 和 JavaScript。
4. 检查完整性、可读性、应用身份、依赖痕迹和敏感信息。
5. 将与 ASAR 逐文件一致的 10 个文件保存到 `runtime/`。
6. 生成 `docs/runtime-0.1.3.sha256`，由 `npm run check:reference` 持续验证。

该过程产生的是**运行时参考快照**，不是原始开发工程。运行时 JavaScript 和 CSS 未做强混淆，仍可审查变量、注释、数据结构和功能逻辑，但原构建已经移除了部分模块边界并把 Vue 组件编译成渲染函数。

## Source-equivalent 重建

当前 `src/` 从所有者产出的 0.1.3 运行时重建，保留可观察行为、应用身份和本地数据兼容性，并接入 `electron-vite` 构建：

- `src/main/index.js` 和 `src/preload/index.js` 保留可读逻辑，但原先可能存在的模块边界已不可恢复；
- `src/renderer/` 保留已编译的 Vue 渲染函数、HTML 和 CSS，可编辑、可构建，但不是原始 `.vue` 文件；
- 恢复出的 renderer 直接包含 Vue 3.5.40 与 lunar-javascript 1.7.7；项目所有者的 0.1.3 安装包使用 Electron 43.2.0，0.1.4 开发/打包运行时升级到 Electron 43.3.0；
- `npm run check` 同时验证黄金参考、IPC/安全契约、当前构建和 `out/` 产物结构。

这些检查用于发现行为边界、桥接接口和构建结构的意外变化。它们**不宣称**当前构建能逐字节复现原始 0.1.3 安装包；构建工具版本、归档元数据、编译顺序、签名状态和 source-equivalent 输入都可能使二进制不同。

## 目录语义

- `runtime/`：从原始 0.1.3 `app.asar` 提取并按哈希锁定的不可变黄金参考。除纠正可验证的归档错误外，不在这里开发新功能。
- `src/`：当前时间大师 0.1.10 的唯一可编辑构建输入；`npm run build` 将其编译到 `out/`。
- `legacy/litecal-0.1.0/`：仓库最初 LiteCal 0.1.0 的历史模块化源码，仅供理解和迁移模块边界，不参与当前根构建。
- `out/`：本地生成的构建目录，不是权威源码或 0.1.3 参考。
- `release/`：本地打包产物目录；0.1.4 及后续产物不得覆盖或冒充原始 `v0.1.3`。

## 0.1.4 正式版本边界

- `0.1.4` 于 2026-08-12 定版为 Windows x64 正式版本；正式 NSIS 产物文件名为 `TimeMasterV2-Setup-0.1.4.exe`。
- 0.1.4 产物从上述 source-equivalent 输入构建，不是原始 0.1.3 二进制的逐字节复现；原始 0.1.3 安装包来源、大小和哈希继续按本文件前文保留。
- 0.1.4 安装包未经过 Authenticode 签名，Windows 可能显示 SmartScreen。其 SHA-256 必须从最终实际产物计算并与该产物一起提供，不能复用 0.1.3 的哈希。
- 本节记录版本定版与产物约束，不表示安装包已经上传到 GitHub Release；是否可下载以发布渠道中的实际附件为准。

## 版本和发布规则

- `v0.1.3` 仅代表原始所有者安装包及其不可变运行时参考；不要移动该标签来指向后续开发构建。
- 当前开发版本为 0.1.10。任何后续开发安装包都必须使用更高且明确区别于既有正式版本的版本号。
- 每个新发布版本应有 Git 标签、变更记录、校验文件、构建命令和已知限制。
- 未签名版本必须在 Release 和 README 中明确提示 Authenticode/SmartScreen 风险。
- 在实现签名和受控构建前，不应使用“可重现二进制”或“bit-for-bit reproducible”等表述。

## 后续维护原则

- 新功能和修复只进入 `src/`，不能只修改安装包、`release/` 或黄金参考。
- 逐步把主进程拆分为存储、备份、提醒、窗口、IPC 和导出模块。
- 逐步把渲染层恢复为 Vue 单文件组件和可测试的 composable，同时用黄金参考、契约测试和脱敏 UI fixture 保持行为与数据兼容。
- 数据格式、迁移、备份恢复、费用导出和专注状态变更必须补充自动化测试。
- 发布前执行 `npm ci`、`npm run check`、打包烟雾测试、依赖/秘密扫描，并计算最终安装包哈希。
